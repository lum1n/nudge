# 6. Writes wait for a person; keys stay with the host; people add APIs, not code

Nudge should use the services its people rely on (a weather API, a journey planner, a home server) without any of them being built in. People add them in chat as connectors: a base URL, what to use it for, optional docs. Two things then need a person rather than the model: deciding that a request which changes something may go ahead, and holding the key it is sent with.

**Approvals are a core primitive.** An extension that wants a person to agree first calls `requestApproval` inside its own commit and returns at once; the approval sits in the room's `nudge.approvals` doc, every client shows it, and any room member can decide it (whoever asked included). On approve, Nudge marks it approved, runs the extension's `approvals[kind]` handler, stores the result and sends the outcome to the model as follow-up input; a denial is sent as well, so the model doesn't retry. Handlers are looked up when an approval runs, so a reload's handlers apply. An approval found still `approved` after a crash is marked failed and never run again: a write that might have happened once must not happen twice. Connectors and the MCP bridge both use it. Approvals trust the extension name passed to `requestApproval`, so one extension could file an approval that runs another's handler; a person still has to approve it, and in-process extensions can already reach each other, so this is noted rather than fixed.

**Secrets live outside the database.** `ExtensionHost.secrets` is a per-extension `SecretStore`: values per scope (usually a room), AES-256-GCM at rest under a key file next to it or `NUDGE_SECRETS_KEY`, so database copies and backups hold no keys. Keys are entered in the web Connectors panel or an unechoed CLI prompt, never in chat. The harness adds them to requests itself, and `scrubSecrets` replaces any echo of them in responses and errors before the result goes on, which then passes through `RedactingModels` like every tool output (ADR 2).

**Connectors are data, scoped like memory.** A connector belongs to the room it was added in. The owner can share a keyless one with every room from the host; a keyed one can't be shared, because its key belongs to the room. Reads (GET, HEAD, and `POST`/`PUT`/… paths a person marked as reads, such as a GraphQL endpoint) run freely. Other methods need an approval, and so does adding a connector or changing its base URL: otherwise text the model read on a web page could have it add an attacker's URL and send conversation context there in query strings. Calls are held to the connector's origin (paths can't escape it, redirects are followed only within it), and localhost and private networks are blocked, checked against every address the name resolves to, unless a person turns `allowPrivateNetwork` on for that connector. The model can't set keys, read paths or private-network access. A DNS answer that changes between the check and the connection is a known gap.

OpenAPI specs are read only as JSON (no YAML) and cached; the model searches and describes operations instead of loading the whole spec. GraphQL schemas aren't read yet.

Room-socket handlers that change documents outside a tool or approval (the Connectors panel) get `ExtensionHost.documents()`: snapshot, watch and commit once the assistant is open. Room-socket clients are told whether the player is an admin.
