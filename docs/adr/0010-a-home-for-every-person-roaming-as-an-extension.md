# 10. Every person has a home; roaming to other assistants is an extension

Until now a player belonged to one assistant: a record in its directory, tokens that work only there, and own memory that stays there. People want more than one. One person can have a private assistant on a server of their own, be in a team's assistant on someone else's, and start shared rooms on either. To them that is one person in several places, so it should look like one: one sign-in and one name, with their settings carried along. The apps will be published, so the hosts are anyone's, and no Nudge host can count on another being run by the same people.

**A person's home is the assistant they joined first.** They are a member of its lobby, and the home vouches for them everywhere else. Their address is the home's URL and their player id there, written `vegard@nudge.example.com/robin`. Joining another assistant goes like this: that assistant's admin invites the address. The person's app asks the home for an assertion, signed with the home's Ed25519 key and naming the assistant joined and a short expiry. The app hands it to the other assistant, which checks it against the key the home publishes and creates a local player marked with that `home`. The app gets a local token for that player, as pairing gives one today. From then on the visited assistant treats them as any player: admin rights, budget share, spend and rooms are its own. Nothing about token checks changes, so core gets no authentication hook. If a home disappears, the identities it vouched for are gone with it. The players stay on the assistants they visited, with nobody left who can sign in as them again. Backups cover a dying machine; identities that can move between hosts are left for later.

**A person's settings live at home in a profile and travel with them.** A new document per player, `nudge.profile`, holds display name, avatar, time zone, language, notification preferences and per-player extension preferences. An extension declares what it keeps there with an optional `playerSettings` schema in its manifest, as it does `settings` for the assistant. A visited assistant fetches the profile, signed, when the person joins. The home sends a fresh one to every assistant the person is in when it changes. The profile is edited at home only; a visited assistant shows it and uses it. Their time zone reads the times of nudges they set, and their language is the one the assistant answers them in.

**Personal data roams only where the person allows it.** Own memory is the one setting that holds personal data, and a host it reaches sends it to that host's model provider (ADR 2) and keeps its values in that host's vault (ADR 9). So it is carried per visited assistant, and only once the person turns it on there. The home stays its source: `remember` everywhere on a visited assistant sends the fact home, and the home passes it on to the assistants the person carries it to. Values a person made private belong to the vault they were made in and are not carried; they are made private again where needed. A carried fact travels with the values behind its placeholders, and the receiving host protects them in its own vault, since one host's placeholders mean nothing, or something else, on another.

**What goes between hosts is signed and encrypted.** Profiles and own memory are personal data, and HTTPS only protects them on the wire to whoever ends the TLS connection. So each assistant has an Ed25519 key to sign with and an X25519 key to receive with, and every message between hosts, the join assertion an app carries included, is signed by its sender, names its recipient, and is encrypted for that recipient alone. Hosts pin each other's keys when they first meet. A host can rotate its keys: the old signing key signs the new ones, and a host that pinned the old key follows that chain when a message under it no longer checks out. That helps routine changes, not a leaked key, since whoever holds the old one can sign for keys of their own; after a leak, people join again.

**Roaming is the extension `ext-federation`.** It publishes the home's key and profile, signs assertions, takes joins, and keeps the profiles and own memory of roaming players in sync. Without it, an assistant works on its own as it does now, and that is a choice a host makes in `nudge.json`. Core gives it what it can't do from outside: the profile document, a `home` on a player, and HTTP routes for extensions, under `/v1/a/<assistant>/ext/<extension>/`, each saying whether it needs a player's token. One assistant asking another for something, such as whether someone is free on Thursday, is a later extension on top of this one, and it acts as a player of the other assistant with the approvals that brings.

**Push is an extension too, and the project runs a relay.** A host can't hold the published apps' APNs key or Firebase service account, so `ext-push` takes Web Push, APNs and FCM out of the server. A host sends through its own keys or through the relay the project runs. Registering with the relay gives an app an opaque handle, signed by the relay, that a host needs to reach that device. Payloads are encrypted for the device, as Web Push is for a browser, so the relay forwards them without reading them.

**The apps sign in once, at home.** They keep the home account and get from it the assistants the person is in. Each has a token of its own in the keychain, and the rooms of all of them are shown together, grouped by assistant. Settings are edited once, in the profile.

**Room names can be changed.** The lobby's by an admin, a personal room's by its owner, and a shared room's by its members. A room keeps its id when renamed, so links and notifications still work; "lobby" stays the kind of an assistant's main room, whatever it's called.

What this doesn't do: a room still lives on one assistant, and its members are that assistant's players. There are no rooms shared between hosts, so a conversation's history and the values in it stay on the host where it took place. A visited assistant sees what it is told: the profile, and the own memory the person carries there. Leaving is done at home, which tells the assistant left: the person's tokens there stop, and so does the memory carried from home. It can still keep what it was sent, as any host can.
