# 11. A server has an owner; it sets itself up, updates itself, and can be made from the app

Setting up Nudge today means cloning the repo, building it, exporting an API key, writing `nudge.json` by hand, running `nudge serve` in a terminal and putting a TLS proxy in front of it. An assistant exists only as an entry in that file, so adding one, or changing its model, means editing the file and restarting. People should be able to do all of this on their own: start a server in a few minutes, and from the app launch new assistants on it, or on a new server they rent.

**A server is one running Nudge on Linux, and it has owners.** It is one process and one data directory, and it serves any number of assistants. Its owners create, change and delete assistants, set provider keys, and see health, updates and backups. Being an assistant's admin doesn't make you an owner, and the reverse holds too. An owner is an address (ADR 10), so no new kind of account is needed. On the server that is their home, an owner signs in as their player. On any other server, the app asks the owner's home for an assertion naming that server and trades it for a server token, the same way joining works. The server API lives under `/v1/server/`, next to the per-assistant API, and its tokens (`nudge_server_…`) are kept apart from player tokens. A server's first owner is whoever claims it at setup; owners can add more.

**An assistant is made for someone.** "For me" creates it and has the owner join it from home, so they keep one home. "Someone's home" creates it with a pairing link for the person it's for, who becomes its first admin, for example an employee's own assistant on an office server. On a new server whose owner has no home yet, the first assistant becomes their home. An assistant's slug can't change, since it is part of every address of the people at home there; its display name can. Deleting an assistant takes a backup first, tells the homes of its guests that it closed, then removes its database, data and keys.

**The server owns its config.** `nudge.json` lives in the data directory (`NUDGE_HOME`, `/data` in the image), and the server writes it through the server API, the way `PUT /admin/extensions` does today. Assistants open, change and close while the server runs; a new model, instructions, budget or time zone takes effect without a restart. Hand edits are still read on reload. A server with no config starts in setup mode instead of quietly making a default assistant.

**Encryption on by default, and the backup key is the one to keep.** A database a server makes is encrypted under a key of its own in `<database>.key`, as `nudge db encrypt` makes one (ADR 7 left this to the host; it is now the default); one that exists unencrypted stays so until encrypted. Backups hold every database with its key file and every extension's secrets, the federation keys among them, so a backup and the backup key bring a whole server back. Backups are on by default, and setup ends with a recovery kit: the backup key, sealed with a passphrase. Losing both the server and the kit loses its people's history and the identities it vouches for.

**Model keys are your own and are kept on the server.** The default is an Anthropic or OpenAI key pasted in the setup wizard or the app, tested with a small call, and stored encrypted in the server's secret store, for the whole server or one assistant. The server API takes keys and never returns them. Environment variables still work and win, for people who manage their servers that way. A platform's own models, such as exe.dev's LLM gateway, and local servers such as Ollama are offered when detected, but only when someone picks them, never as the default.

**Setup is a wizard behind a one-time code.** In setup mode a server prints a URL, a setup code and a QR code, so it works from a terminal and from `docker logs`. `/v1/setup/` answers only in setup mode and only with the code, and refuses once claimed. The web wizard, `nudge setup` and the apps all use it. It claims the server, names the first assistant, sets the model, makes the owner the first player and admin, sets how the server is reached, pairs a phone and hands over the recovery kit.

**Reachability is picked, not configured.** The server knows how to be reached through: the HTTPS proxy of the platform it runs on (exe.dev, whose forwarded headers it then trusts), its own domain with a certificate it gets over ACME, Tailscale (with Funnel when it must be public), and a named Cloudflare Tunnel. A LAN-only server is advertised over mDNS. The public URL is set once on the server and drives pairing links and the federation address, which replaces `--public-url` and the federation `server` setting. Because a server's address is in every address of its people, it can move: the server signs a `nudge.moved` claim with its current key, and peers follow it and re-pin, as they follow key rotations. Moving with a leaked key is no safer than rotating with one. The other way round, a server can join its owner's tailnet itself, so it reaches a home that is only in that tailnet: it runs Tailscale in userspace mode, without root, and the owner approves it from the app. Only requests to tailnet addresses go through it.

**Servers update themselves.** Releases are self-contained tarballs (Node and the prebuilt SQLite module) for linux-x64 and linux-arm64, signed by the project, and an OCI image that carries only a launcher. The launcher runs the newest release in the data directory. Every day the server checks its channel (stable by default), verifies a new release's signature, takes a backup, starts the new release and rolls back if it fails its health check. This works the same under Docker, on exe.dev and from the installer, so pulling a new image isn't how a server updates. Owners see updates in the app and can pause them.

**The app can make a new server, starting with exe.dev.** The person signs in to exe.dev in the app: the app makes an SSH key of its own and opens `ssh exe.dev` with it, showing its screen, where exe.dev asks for their email and mails a link that adds the key to their account, new or not (exe.dev's host key is pinned). The app then mints its exe.dev API token from that key on the device, scoped to the commands Nudge needs, as exe.dev's local key creation describes. A token minted on a computer can be pasted instead. Key and token stay in the app's keychain and are never sent to a Nudge server. The app creates a VM from the Nudge image with a fresh setup code, makes its HTTPS proxy public (people authenticate with Nudge's own tokens, not an exe.dev login), waits for the setup API, claims the server and makes the first assistant. A server not claimed within minutes closes its setup API, and the app offers to remove the VM. Removing a server from the app downloads a backup, deletes its assistants so their guests are told, then removes the VM. Other providers are drivers behind the same steps. The list of servers a person owns is kept at their home, so all their devices see it.

**A laptop runs one standalone assistant, not a server.** The desktop app can run one assistant for its owner, with federation and the server API off. A laptop sleeps and moves between networks, so it is never anyone's home and never visited by other assistants. It pairs on the LAN or over Tailscale.

What this doesn't do: servers don't run on Windows or on serverless platforms (the Durable Object host is still parked). Signing in to exe.dev rides on its SSH sign-up screen, so a change there can need a change in the app. Identities still end with the home server that vouches for them (ADR 10); `nudge.moved` lets a server change address, not a person change server.
