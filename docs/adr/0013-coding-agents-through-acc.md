# 13. Coding agents through ACC, with its SSH client and a key of the assistant's own

The assistant should start, watch and steer the coding agents people run on their machines (Claude Code, Codex, Cursor, Copilot CLI, pi, opencode), as the `acc` extension. [ACC](https://github.com/lum1n/acc) already drives all six over plain SSH with nothing installed on the machines: `acc-core` speaks each agent's headless protocol and keeps sessions detached on the host, and `acc-ssh` is its own SSH client (pure-Rust russh). The Sessh app embeds both.

**A napi binding in ACC, not its wasm one.** ACC's wasm binding has the core but leaves SSH out, since russh needs sockets and tokio, which wasm lacks; it would have meant another SSH client in JavaScript beside the one ACC has and tests. ACC gets `crates/acc-node` instead, the same objects as its Swift and Kotlin bindings (`SshHost`, `RemoteSession`), with the core's values in their serde shapes as the wasm binding passes them. It is built and released the way Wired's Node binding is: archives per platform on ACC's GitHub release, pinned by version and hash in `packages/release/scripts/acc.sh`, shipped in a release's `acc-node/` and fetched into a checkout's `.acc-node/`. Without it the extension loads and `nudge doctor` says what is missing.

**The assistant's own key, and host keys pinned on first use.** acc-ssh takes a password, a private key or an ssh-agent, and leaves where keys come from to the embedder. The server is not someone's desktop with an agent and a `known_hosts`, and people don't run commands on it (ADR 11). So the extension makes an ed25519 key the first time, keeps it in its secret store, and tells people the line for `authorized_keys`. It pins each machine's host key the first time it connects and refuses a different one later. Only an admin can trust a new key, through an approval. Agent and password logins remain for machines set up that way.

**This machine needs no setup.** Most people run agents where Nudge runs, so the extension reaches that machine's sessions as `local` with nothing configured. acc-ssh gained `Host::local()`, which runs the same session scripts with `sh` instead of over SSH, so a session started by Sessh there can be followed just like one on another machine. The scripts get a login's environment (`HOME`, `PATH`, the locale…) and not Nudge's, which holds its keys. An agent started there can still read what Nudge's user can, Nudge's data included, which is why starting one waits for approval by default and `"local": false` turns it off.

**Following a session is a watch, and its permission requests are approvals.** The room that starts a session follows it: one reader per followed session runs while the server does, and is attached again after a restart. ACC replays a session's log from the start to rebuild its state, so what happened before the reader caught up is not told again, except requests still waiting. A finished turn, an error or an exit reaches the room as input like a watch's, so push and chat bridges deliver it. A permission request becomes an approval in the room. Denying an approval used to run nothing, so approvals gain denial handlers (`ExtensionParts.denials`): denying tells the agent no rather than leaving it waiting. As in ADR 12, the approvals' payloads stay empty, and what they are for (the session's request, the directory to start in) is kept by approval id, since placeholders could change a path or a machine's name.

Left for later: a room page that streams a session's transcript, sessions people started by hand in a terminal (ACC's `observer` library finds and takes them over), and withdrawing an approval when another client answered the request first; for now the room is told it no longer matters.
