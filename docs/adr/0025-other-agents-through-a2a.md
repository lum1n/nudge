# 25. Other AI agents talk with the assistant over A2A, beside peers

Peers (ADR 23) links Nudge assistants: both sides' admins agree, and every message is signed and sealed through federation. That reaches only other Nudges. People also want the assistant to use agents built elsewhere (a company's support agent, one made with Google's ADK or LangGraph), and to let such agents ask theirs things. A2A, the Linux Foundation's Agent2Agent protocol, is what those agents speak: an Agent Card says where and how to call an agent, and JSON-RPC methods send it messages and read the tasks they start.

**A2A is an extension of its own, not peers' new wire.** Peers keeps its linking, its threads and its end-to-end encryption, which A2A has no place for: A2A trusts TLS and a security scheme on the card. Moving peers onto it would have cost that sealing to gain a standard only Nudges use. So `a2a` stands beside `peers`, needs no federation, and an assistant may have either or both. What the two share is the shape: whoever calls in is a guest player in a room of its own.

**An agent that calls in is a guest, as a linked assistant is.** An admin lets it in by name, and gets a bearer token to hand over, shown once; only its hash is kept. It gets a player with no token of Nudge's and no admin rights, and a shared room with the admins, where only what `offer` turns on is on. Each message it sends is an A2A task, posted in that room as its player's, so redaction, the per-player budget, the room's extensions and approvals hold as for anyone. The answer is the room's answer, shown as its player may see it (ADR 9). Answers that wait on an approval are what A2A's tasks are for: the task stays working, says what waits, and completes once the room's people decided, then is pushed to the agent if it asked for that. Peers needed a "late" follow-up for this; here it is the protocol's own state. A blocking call waits `waitSeconds` and then returns the task still working, so a slow approval holds no connection open. Tasks are kept in a document, so `GetTask` answers after a restart, and one cut off by it is answered again from the message it already posted.

**Agents this assistant calls are added by an admin, by their card.** In chat, `add_agent` files an admin-only approval: otherwise text the model read could add an address to send conversation to, as with connectors (ADR 6). The settings page and its route add one directly, with a token if it needs one; tokens live in the extension's secrets and are never typed in chat. `message_agent` sends what whoever asked may see, and returns the answer as untrusted data (ADR 20): the agent's words, not instructions, so a turn that read them asks before it sends anything else out. A message from an agent that calls in is marked the same way. An agent that takes longer than a turn goes on in the background: a durable task checks on it every `pollMinutes` for up to `replyHours`, a push notification to `server` makes it check at once, and the room hears the outcome as a fired nudge. Answers name their A2A context, so the model can go on in it, including when the agent asks for more (`input-required`).

**The wire is the official SDK's.** `@a2a-js/sdk` parses and writes A2A's JSON (its JSON-RPC transport handler, with a request handler of ours on Nudge's documents) and is the client that calls agents. The tests run its client against this extension, so what it accepts is what other implementations send. Only HTTPS and Wired addresses are reached, for agents and for push alike.

What this doesn't do: streaming (the card says so), the HTTP+JSON and gRPC bindings on the serving side, signed cards, OAuth, and an agent calling in being sent to more than its one room. Rooms of agents that call in can't message agents, so agents don't chain on their own. The apps' settings for it exist on the web; the Android and Apple apps don't have them yet.
