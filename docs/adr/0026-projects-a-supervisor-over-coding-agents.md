# 26. Projects: a supervisor over coding agents

The acc extension (ADR 13) lets the assistant start and steer one coding agent at a time when someone asks. People want more: say "New project: a tiny API with tests" and have the assistant take it from idea to merged code on its own, using their own Claude and ChatGPT subscriptions, telling them how it goes and taking their direction while it runs. That needs a plan the assistant keeps, machines for the agents, secrets the agents get, and stops where a person must decide.

**A project is a room.** `project_create` makes a shared room with the people of the room it was asked in, and the project's state lives in a document keyed by that room: the brief, the milestones and their tasks with acceptance criteria, each task's branch, agent and pull request, the VM, the names of its secrets, the budget and how many agents may work at once. A prompt section puts the summary and the supervisor's rules in front of the model every turn, so it stays on track after the history is compacted. People steer it by writing in the room, as in any room; a message during a turn steers that turn.

**Each project gets its own exe.dev VM, which the phone launches.** The exe.dev token stays on the device (ADR 11), so the server can't make a VM. The extension asks with an approval that carries a client action, `exe.new`: the Nudge app adds the assistant's SSH key to the person's exe.dev account, makes the VM with the token, and approves with the VM's name and SSH host as inputs. The web, which has no token, says to open the app. Deleting the VM at the end works the same way with `exe.rm`. The VM becomes a machine of the acc extension, added at runtime and usable by the project's room only; it logs in with acc's own key and pins the VM's host key like any other machine. acc needs nothing installed there; the extension installs the agent CLIs, `gh` and Node where missing, and clones the repo.

**Approvals can ask for values.** An approval may name inputs, such as a key, with password fields for secret ones. The value goes with the decision to the extension's handler (`ApprovalRun.inputs`) and nowhere else: it is not stored with the approval, not in the room's history, not in what the room is told of the outcome (which is scrubbed of it), and not given to the model. Chat bridges and the CLI can't take one, so they say to approve in the app. This replaces asking for keys in chat, which would leave them in the history and send them to the model.

**Secrets reach agents but never the model.** `project_request_secret` asks for one with such an approval. The value is kept in the extension's encrypted secret store, scoped to the project or, for the person's own logins (`CLAUDE_CODE_OAUTH_TOKEN`, `CODEX_AUTH_JSON`, `GH_TOKEN`), to their account. It is also protected in the vault, so a value pasted into chat becomes a placeholder. It goes to the VM only on a script's standard input, into `~/.nudge/project.env` (mode 0600), which login shells load; scripts themselves never hold it, so it isn't in the VM's process list. Everything an agent prints passes the acc extension's scrubbers before the room or the model sees it: transcripts in `acc_read`, what a followed session tells the room, and the summaries of its permission requests. The model only ever hears that a secret is set. ACC 0.2's sessions take no environment of their own, so agents get the variables through the login shell; once ACC takes an `env` per session, the extension passes it there.

**Fully autonomous, with gates.** Once the plan is approved, the extension starts an agent on each ready task of the active milestone, in its own git worktree on `task/<id>`, with the task, its criteria and the rules (push the branch, open a PR, end with `DONE <url>` or `BLOCKED <why>`), at most `maxAgents` at a time. acc's follow events wake the supervisor in the project room; it records the PR, starts a reviewing agent, answers routine questions with `acc_send`, and brings people only what is theirs. A timer checks on agents that have been quiet for `stallMinutes`, sends a daily digest, and says when a milestone is ready for its gate. Its wake-ups are capped per hour. The stops are: the plan, each milestone's merge (the PRs merge in order with `gh` on the VM once someone approves), a secret, the budget's warning level (the project pauses and asks), blockers the agents can't get past, and the permission requests acc already turns into approvals.

**What the model sees and doesn't.** It sees the brief, the plan, task states, PR addresses, CI results, the VM's name and host, the names of secrets, spend, and agents' transcripts with secrets scrubbed. It never sees a secret's value, the exe.dev token (it never leaves the phone), or the assistant's private key. The agents on the VM see the project's secrets and the person's logins; that VM is theirs, and deleting it ends that.

What this doesn't do yet: a per-session environment in ACC (it needs an ACC release), a durable task for the supervisor's timer (the timer runs in the process and keeps its state in the project's document, so a restart loses nothing but a minute), a denial with a comment (people say what to change in the room instead), and the Apple app's parts, which wait for a Mac to be compiled. Whether the default exe.dev image and a token scoped to `new` allow `ssh-key add` hasn't been tried on a real account; when it fails, the app tells the extension, which gives the key to add by hand.
