# 30. Cards update in place, open links after asking, add events to calendars and draw diagrams

ADR 27 made cards and ADR 29 gave them maps and charts. Using them showed what was still missing: a card that follows something as it changes, a way to send people to a page, something to put in a calendar, a flow drawn as boxes and arrows, more ways to answer, and images in the native apps.

**A tool can show its card again, changed.** `Nudge.ui.update(conversationId, callId, card)` checks the card as `show_ui` does, finds the card the tool call showed, and writes a `nudge.ui-update` entry `{ callId, card }` with a passive write, which places it at once, even mid-run, and starts no turn. The projection gives the tool part the latest valid update as `details.ui`, so every client draws it without knowing about updates. An update starts the card over: the press mark goes, and `pressed` shows only a press after it, so its buttons work again. A press checks the latest card. The model updates a card with `update_ui { call_id, card }`, giving the whole card; extensions do it through `host.assistant().ui`. The model doesn't see the update itself, as it changes nothing in its context; a tool that updates a card says so in its own result when the model should know. An update rides on the conversation like a press does, so it shows wherever the card's answer does.

**A button can open a page.** A button with a `url` (https only) isn't pressed. The app names the page's site and asks before it opens it, as a page in the chat can't prove where a link goes, and nothing reaches the room. The server refuses a press on such a button, which an app from before this would send as an ordinary press.

**An `event` block** is something for a calendar: a `title`, a `start` and an optional `end`, each a day (`2026-11-03`, all day) or a time with its offset from UTC (`2026-11-03T18:00+01:00`). A time without an offset would mean whatever zone the reader is in, so the schema requires one. `location` and `notes` are optional. Each app adds it to the reader's calendar its own way, without asking for access to the calendar: the web app hands the browser an .ics file, Android opens the calendar app's new-event screen filled in, iOS shows the system's event editor, and macOS hands Calendar an .ics to import.

**A `diagram` block** is boxes (`nodes`, each an `id` and a `label`) joined by arrows (`edges`, each `from`, `to` and an optional `label`), in rows going `down` (the default) or columns going `right`. Each app lays it out the same simple way, so the card holds no coordinates: a node goes one row past the furthest of the nodes with arrows to it, a cycle is broken at its earliest node, and within a row nodes sit by the middle of where their arrows come from. Up to 30 nodes and 60 arrows keep that readable on a phone; a wider diagram scrolls sideways.

**Two more fields.** `choices` takes any number of its `options` and sends them as a list. `range` is a slider from `min` to `max` (0 and 100 when absent) in `step`s (1), and sends what it shows when left alone. An app from before this shows both as text fields, so the server also takes `choices` as comma-separated text and `range` as a number in text, checked the same way.

**Charts can be read as a table.** Each app has a button under a chart that shows its values as a table instead, for reading them exactly and for screen readers.

**The native apps show images.** Android and Apple show a card's `image` block from the room's attachments, fetched and kept as the apps do for messages, and its `alt` text while it loads or when it can't.
