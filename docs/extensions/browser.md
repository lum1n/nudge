# Browse the web

`extensions/browser` gives the assistant a `browse` tool. The room's model hands it a task ("find a 2027 Mercedes GLC for sale in Oslo on finn.no"), and a browser agent on its own model works a real browser until it has the answer:

```json
{ "from": "./extensions/browser", "settings": { "model": "anthropic/claude-haiku-5-5" } }
```

- `model` is `provider/model` and defaults to `anthropic/claude-haiku-5-5`, which did best in our tests at a fraction of the cost of larger models. Without an Anthropic key, pick one from your provider, such as `openai/gpt-5-mini`. Weak models struggle with multi-step browsing.
- The model never sees the screen. It reads each page as compact text (open dialogs first, one line per search result) and acts on element refs, so any tool-calling model can drive it and every page passes through the same redaction as the rest of Nudge.
- The browser is headed, because many sites block headless ones, and runs on its own virtual display (needs `Xvfb`). Chromium is downloaded the first time a room browses, into `~/.cache/ms-playwright`. The server image has Xvfb and Chromium's libraries and releases bundle the extension, so a server made from the image can browse once it is turned on; one made from an image older than 0.3.0 can't, and says so. Each room keeps its own browser profile under `<database>.extensions/browser/profiles`, so cookies and consents stick; a room's browser closes after `idleMinutes` (default 10).
- It does not buy, book, send, sign up or enter your details on its own. When a task needs that, it gets everything ready, stops, and asks the room to approve the exact step ("Click \"Pay 1 290 kr\" on sas.no to book …"), as an approval like any other: in the chat, `/approve` in the terminal, and the apps. Approving it starts the browser agent again in the room's browser, where it left off, allowed to do exactly that step; the room then hears how it went. Deciding waits until that run is done. The browser holds it to this in code, not only by telling the model, since a page can tell the model otherwise: it refuses, until someone approves, a click on (or Enter or Space on) a button whose label pays, buys, books, sends, deletes, publishes, confirms or signs up (in English or Norwegian, like "Pay 1 290 kr", "Send", "Slett annonse", "Place order"; cookie banners, "Go to payment" and links to other pages don't count), typing into a password, one-time-code or card field, sending a form that isn't a search (POST) on a login form or on a site you're logged in to (one with a way to log out), and Enter in a chat box on such a site. One approval lets one such step through. It logs in with your help: the first time a site needs a login, `browse` stops and asks you to open the room's **Browser** page in the web UI, a live view of that room's browser. Log in there yourself (password, BankID, a code, whatever the site asks) and press **Done**. With "Remember logins I type here" ticked, the username and password you typed are saved, and next time the agent's `browser_login` tool fills them in on that same host by itself. The model never sees them: password and one-time-code fields always read `[hidden]` in its view of a page, saved values are hidden wherever they appear, and the tools never return them.
- While `browse` runs, the chat and the terminal show what it is doing, one short line at a time (`Clicking "Search"…`).
- When `browse` stops for a login, the chat shows an **Open the room's browser to log in** button. The Browser page lists the room's saved logins (site and username, never the password) with a **Forget** button.
- Everyone in the room can open its browser. The first one in controls it; the others watch and can **Take control**.
- Saved logins are kept per room in `<database>.extensions/browser/logins/logins.enc`, encrypted (AES-256-GCM) under the key file next to it, both readable by their owner only, or under `NUDGE_BROWSER_KEY` (32 random bytes, base64) when you set it. The key protects copies of the database and backups; whoever has the key can read the logins.
- The browser does not reach localhost, private or link-local addresses, or `.local` names, so the agent cannot be steered into your router or other machines at home. Set `"allowPrivateNetwork": true` to allow it. Names that resolve to private addresses are not caught.
- **Site notes:** after a run that took a few actions, the browser agent writes short notes on how it used each site (where the filters are, URL parameters that worked, which button closes the cookie dialog), and gets them back the next time it reaches that site in the same room. Each room keeps its own, so a page that steers what the agent writes in one room cannot reach the others. Notes are kept as at most 8 plain lines of 200 characters per site, with tags, code fences, control and invisible characters removed, for the 100 sites a room used most recently, and are shown as hints, not instructions. They hold no results and nothing about the user, and cost one small extra request. Notes from before they were kept per room were shared by every room, so they are dropped. `"siteNotes": false` turns them off.
- **Page tools (WebMCP):** a site can offer agents its own tools with `registerTool` on `document.modelContext` (or the older `navigator.modelContext`): a search, an add to basket, a booking. Each one has a name, a description and an input schema, and the browser agent can call them instead of clicking through the page (ADR 28). The page header lists them (`Page tools (WebMCP): search, add_to_basket`). `browser_page_tools` describes them, and `browser_call_page_tool` calls one. A tool the page marks read-only (`annotations.readOnlyHint`) runs at once. Any other tool is held for the room's approval, like a click on Pay, pinned to the site, the tool and exactly its arguments. A tool that asks for the user (`requestUserInteraction`) fails, because nobody sits at that browser. A call that runs longer than 30 seconds fails too. Results are cut at 8,000 characters and reach the room as untrusted data, like the rest of the page. Before any page script runs, a small script records the tools pages register. Where the browser has no `modelContext`, it stands in for the API, so pages that check for it find it. `"webmcp": false` turns this off and leaves the API out, for a site that treats it as a sign of automation. To use Chrome's own implementation while it is in trial, pass its feature switch in `"chromiumArgs"`.
- `nudge doctor` also checks the browser model's credentials.
- Install its browser once with `pnpm -C extensions/browser exec patchright install chromium`.
- `pnpm -C extensions/browser eval -- --model anthropic/claude-haiku-5-5,openai/gpt-5-mini` runs a set of everyday tasks against each model, twice each (`--runs 3` for more), through the same redaction as Nudge, after `pnpm build`. It writes each run's result, every request the providers got, and a summary table (answered, expected answer seen, steps, seconds, cost, leaks) to `extensions/browser/.eval/`. Some tasks carry made-up personal details; a leak is one of them reaching a request as it is, and makes the run exit with an error. Keys come only from your environment; without one for a model it stops before opening a browser.
