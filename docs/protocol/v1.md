# Nudge protocol v1

How clients talk to a Nudge host: a WebSocket for live views and plain HTTP for commands. The reasons are in [ADR 5](../adr/0005-nudge-owned-client-protocol.md). The TypeBox types in `@nudge/protocol` are the source of truth, and `packages/protocol/schema/v1.json` is generated from them; this page explains them.

> Draft. It describes the target of the work in progress and changes until the web UI and CLI use it.

Every path below is under `/v1/a/<assistant>`, apart from the assistant list. Bodies are JSON and are checked against the schema. Errors are `{ "error": "<message>" }` with status 400 (a bad body or cursor), 401 (no token, an unknown one, or a bad pairing code), 403 (an admin route for a player who isn't one), 404 (also for rooms the caller may not use) or 409 (an approval already decided).

## Signing in

A player gets a token in one of two ways:

- `nudge invite <name>` or `nudge token <player>` prints one, as today.
- `nudge pair <player>` prints a one-time code as a link and a QR code: `nudge://pair?server=<url>&assistant=<name>&code=<code>`. The app sends `POST /pair { code, client: { name, platform } }` and gets `{ token, clientId, player }`. A code works once and expires after ten minutes. It looks like `7K3Q-M9XD` (Crockford base 32), so it can be typed too; case, dashes and spaces don't matter, and `O`, `I` and `L` read as `0`, `1` and `1`.

HTTP requests send `Authorization: Bearer <token>`. The socket sends the token in its first frame, because browsers can't set headers on a WebSocket.

## The socket

`GET /v1/a/<assistant>/connect` upgrades to a WebSocket. Frames are JSON text.

### Client to server

| Frame                                                                        | Meaning                                                              |
| ---------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `{ type: "hello", protocol: 1, token, client: { name, version, platform } }` | Must be first.                                                       |
| `{ type: "subscribe", target }`                                              | `target` is `"home"` or `"room:<id>"`.                               |
| `{ type: "unsubscribe", target }`                                            |                                                                      |
| `{ type: "ping" }`                                                           | Answered with `pong`. Send one if nothing arrived for `heartbeatMs`. |

### Server to client

| Frame                                                                                         | Meaning                                                        |
| --------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `{ type: "welcome", protocol: 1, server: { version }, epoch, player, clientId, heartbeatMs }` | Reply to a good `hello`.                                       |
| `{ type: "snapshot", target, seq, view }`                                                     | The whole view, first after `subscribe`.                       |
| `{ type: "patch", target, seq, ops }`                                                         | Changes since the previous frame for that target.              |
| `{ type: "unsubscribed", target, reason }`                                                    | `reason` is `"not-found"` or `"removed"` (no longer a member). |
| `{ type: "pong" }`                                                                            |                                                                |
| `{ type: "error", message }`                                                                  | A frame the server couldn't use; the socket stays open.        |

`seq` starts at 0 with the snapshot and goes up by one per frame for that target. A client that sees a gap, or a different `epoch` after reconnecting, subscribes again. Patches are sent at most every ~50 ms per target, so a slow client gets fewer, larger patches.

Close codes: 4400 bad frame, 4401 unknown token or revoked, 4404 no such assistant, 1001 the host is shutting down. A client retries with backoff on anything but 4400, 4401 and 4404.

### Patch operations

A path is an array of object keys and array indexes into the view.

| Op                                              | Effect                                                           |
| ----------------------------------------------- | ---------------------------------------------------------------- |
| `{ op: "set", path, value }`                    | Set the value at `path`, adding the key if it's new.             |
| `{ op: "del", path }`                           | Remove an object key.                                            |
| `{ op: "append", path, text }`                  | Append to the string at `path`. Streaming text arrives this way. |
| `{ op: "splice", path, index, remove, insert }` | Change the array at `path` like `Array.prototype.splice`.        |

Operations apply in order. An empty `path` with `set` replaces the whole view.

## Views

### `RoomView` (`room:<id>`)

```ts
{
  room: { id, kind: "lobby" | "personal" | "shared", name, members: Player[] },
  timeline: TimelineItem[],     // the most recent items, oldest first
  hasEarlier: boolean,          // more via GET /rooms/<id>/timeline
  live: { running: boolean, status?: Status },
  queue: { id, mode: "steer" | "followUp", text, author?, clientId?, requestId?, nudge: boolean }[],
  approvals: Approval[],        // pending ones and the ten latest decided, newest first
  memory: { id, text, createdAt, by?: Player, owner?: Player }[], // the room's facts, then members' own shared ones (with owner)
  nudges: { id, message, fireAt, every? }[],
}

Player = { id, displayName }
Approval = { id, summary, status, requestedAt, decidedBy?: Player, decidedAt?, result? }
Status =
  | { kind: "retrying", attempt, at, error }
  | { kind: "compacting" }
  | { kind: "compaction-failed", error }

TimelineItem =
  | { type: "user", id, text, author?: Player, sentAt?, clientId?, requestId? }
  | { type: "nudge", id, text, firedAt }
  | { type: "approval", id, approvalId, summary, status, decidedBy? }
  | { type: "answer", id, status: "running" | "done" | "stopped" | "failed", error?, parts: Part[] }
  | { type: "marker", id, kind: "compacted" | "reset" }

Part =
  | { type: "text", text }
  | { type: "reasoning", text }
  | { type: "tool", callId, name, args, status: "pending" | "running" | "done",
      result?, isError?, details?, output?, truncated? }
```

Item ids are stable, so a client can key rows by them; an answer keeps its id from its first streamed token to its last entry. A user message carries the `requestId` its sender chose, in the timeline and while it waits in `queue`, so that sender can swap its optimistic copy for the real one. Tool `result` and `details` longer than about 8 KB are cut, with `truncated: true`.

### `HomeView` (`home`)

```ts
{
  player: Player,
  rooms: { room, running: boolean, pendingApprovals: number, lastItemAt? }[],
  nudges: { id, roomId, message, fireAt, every? }[],
}
```

## HTTP

| Method and path                           | Body                                   | Reply                                                                                                                                                                   |
| ----------------------------------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /v1/a`                               |                                        | `{ assistants: { name, displayName }[] }`, no token needed                                                                                                              |
| `POST /pair`                              | `{ code, client }`                     | `{ token, clientId, player }`, no token needed                                                                                                                          |
| `GET /me`                                 |                                        | `{ player, clientId }`                                                                                                                                                  |
| `POST /rooms`                             | `{ name, members? }`                   | 201, the room, with the caller as a member                                                                                                                              |
| `POST /rooms/personal`                    |                                        | the room                                                                                                                                                                |
| `POST /rooms/<id>/messages`               | `{ text, requestId, whenBusy? }`       | 202 `{ submissionId }`; the same `requestId` again returns the same id                                                                                                  |
| `POST /rooms/<id>/abort`                  |                                        | 204                                                                                                                                                                     |
| `GET /rooms/<id>/model-view`              |                                        | `{ messages: { role, text }[] }`: the room's next model request as the provider gets it, personal values as placeholders                                                |
| `GET /rooms/<id>/timeline?before=&limit=` |                                        | `{ items, before? }`, oldest first, older than the room view's window or the given cursor                                                                               |
| `POST /rooms/<id>/memory`                 | `{ text }`                             | 201, the fact                                                                                                                                                           |
| `DELETE /rooms/<id>/memory/<factId>`      |                                        | 204                                                                                                                                                                     |
| `GET /me/memory`                          |                                        | `{ facts, shared }`: the caller's own facts, and whether all their rooms show them                                                                                      |
| `POST /me/memory`                         | `{ text }`                             | 201, the fact                                                                                                                                                           |
| `DELETE /me/memory/<factId>`              |                                        | 204                                                                                                                                                                     |
| `PUT /me/memory/sharing`                  | `{ shared }`                           | `{ facts, shared }`; with `shared`, everyone in the caller's rooms, and the model there, reads these facts                                                              |
| `POST /rooms/<id>/approvals/<approvalId>` | `{ approve }`                          | the approval                                                                                                                                                            |
| `GET /rooms/<id>/extensions`              |                                        | `{ extensions: { name, version?, description?, enabled, byDefault }[] }`; the built-in one is always on and not listed                                                  |
| `PUT /rooms/<id>/extensions/<name>`       | `{ enabled }`                          | the extension as above; `null` goes back to the default for the room's kind                                                                                             |
| `DELETE /nudges/<id>`                     |                                        | 204                                                                                                                                                                     |
| `POST /protect`                           | `{ value, kind? }`                     | `{ placeholder }`                                                                                                                                                       |
| `GET /usage`                              |                                        | `{ month, total, mine, budget: { monthlyUsd?, perPlayerUsd? }, months? }`: this month's model spend in USD; `months` (by player and room, newest first) for admins only |
| `GET /push`                               |                                        | `{ publicKey }`: the server's VAPID key for Web Push; 404 when the server sends no pushes                                                                               |
| `POST /push`                              | `{ endpoint, keys: { p256dh, auth } }` | 204; a browser's `PushSubscription.toJSON()`. The endpoint must be HTTPS on a public name                                                                               |
| `DELETE /push?endpoint=`                  |                                        | 204, or 404 when the caller has no such subscription                                                                                                                    |
| `POST /devices`                           | `{ platform: "apns" \| "fcm", token }` | 204                                                                                                                                                                     |
| `DELETE /devices/<token>`                 |                                        | 204                                                                                                                                                                     |

`whenBusy` is `"followUp"` (the default), `"steer"` or `"reject"`. Cursors are opaque strings. A message gets 429 once the caller's or the assistant's monthly budget is spent (`budget` in `nudge.json`).

`/timeline` without `before` starts just older than the room view's `timeline`; `before` from a page gets the page older than it, and a page without `before` reaches the start of the room. `limit` is 50 by default and at most 200; a page holds at least `limit` items, unless it is the last, and at most one more. Item ids match the room view's, so pages and the view join without gaps or repeats. Items that later slide out of the head of the room view's window stay valid: keep them rather than fetch them again.

The `/devices` routes come with native push (APNs and FCM); Web Push is there now.

Admin routes need a player with the admin flag (the first player, or one marked with `nudge admin <player>`):

| Method and path                   | Body                | Reply                                                            |
| --------------------------------- | ------------------- | ---------------------------------------------------------------- |
| `POST /admin/players`             | `{ displayName }`   | 201, `{ player }`, without a token: pair a client for one        |
| `POST /admin/pairing-codes`       | `{ playerId }`      | 201, `{ code, link, expiresAt }`                                 |
| `GET /admin/tokens?player=`       |                     | `{ tokens: { clientId, playerId, createdAt, client? }[] }`       |
| `DELETE /admin/tokens/<clientId>` |                     | 204; sockets using it close with 4401                            |
| `POST /admin/tokens`              | `{ playerId }`      | 201, `{ token, clientId, player }`; the token is shown only here |
| `GET /admin/players`              |                     | `{ players: { id, displayName, admin }[] }`                      |
| `PUT /admin/players/<id>/admin`   | `{ admin }`         | `{ id, displayName, admin }`; the first player stays one         |
| `GET /admin/rooms`                |                     | `{ rooms }`, every room                                          |
| `POST /admin/rooms`               | `{ name, members }` | 201, the room; the caller is not added                           |
| `GET /admin/nudges`               |                     | `{ nudges }`, every room's, soonest first, as in the home view   |

## Extension sockets

`GET /v1/a/<assistant>/rooms/<id>/ext/<extension>` upgrades to an extension's own socket for a room, such as the browser extension's live view. Send `{ "type": "hello", "token": … }` first and wait for `{ "type": "ready" }`; frames after that belong to the extension. It closes with 4401 for a bad token and 4404 when the assistant, the room (for this player) or the extension's socket doesn't exist. These frames are not part of protocol v1.

## Push

A browser subscribed with `POST /push` gets a Web Push when an answer finishes in one of the player's rooms (also an answer to a fired nudge or to an approval's outcome) and when an action there waits for approval. Pushes are encrypted for the browser (RFC 8291), so the push service in between can't read them. The service worker shows each as a notification unless the room is open in a visible tab of the site. By default notifications say only which room has news; `push.preview: "text"` in `nudge.json` adds the start of the text. A subscription stops getting pushes once the token that added it is revoked, and goes once the push service says the browser dropped it. `nudge serve` makes the server's VAPID keys on first start, in `push-vapid.json` next to the first assistant's database.

The payload is JSON: `{ title, body, url, tag, kind: "answer" | "approval", roomId }`, with `url` the room's page (`/<assistant>/<room>`) and `tag` the same for every notification of a room, so a newer one replaces the older.

A device registered with `POST /devices` (once native push is there) gets the same, when the player has no socket subscribed to that room.

## The TypeScript client

`@nudge/client` (`packages/client`) does the client's side for TypeScript: `Connection` keeps the socket (hello, resubscribing after a reconnect or a gap, pings, backoff with jitter, giving up on 4400, 4401 and 4404), `RoomStore` and `HomeStore` apply snapshots and patches (and fit React's `useSyncExternalStore`), and `Api` wraps the HTTP routes with a pluggable `TokenStore`. `NudgeClient` puts them together: leases on views, shared while held; `send` with a fresh `requestId`, shown as pending until the view has the message; and a room's earlier items, from `/timeline` pages and from the head of the view's window as it slides. Its tests replay the recorded stream and run against a real server.

## The Rust client

`clients/rust` does the same for Rust and, through UniFFI, for Swift, Kotlin and Python. `nudge-protocol` has the types, written by hand and checked against `schema/v1.json` and the recorded stream, and `apply`. `nudge-client` has `Api`, `Connection` (a task of its own, with the TypeScript client's reconnect, ping and give-up rules), `HomeStore` and `RoomStore`, and `NudgeClient`, which adds a SQLite cache: the last view of every target, shown while reconnecting and after a restart, and an outbox. A message that doesn't get through waits there and is sent again, with the same `requestId`, once the socket is open; one the server refuses stays failed until it is sent again or dismissed. `nudge-ffi` runs a client on a Tokio runtime of its own and hands views to listeners: a room's timeline as changes (`Reset`, `Append`, `Insert`, `Set`, `Remove`), at most about 30 times a second, and tool arguments and details as JSON strings.

## The Python client

`clients/python` packages `nudge-ffi` as `nudge-client` (module `nudge`) with maturin, and adds an asyncio API: `Client` wraps the commands, and `connection()`, `home()` and `room(id)` return watches to iterate with `async for`, each state whole (the room's timeline rebuilt from the changes) and the latest only. Watches still open at exit are cancelled first, since a listener called during interpreter shutdown crashes Python. `FileTokens` keeps the token in a file only its owner can read.

## The Kotlin and Swift clients

`clients/android` and `clients/apple` wrap the same bindings: an Android library whose `observeRoomState(room)` and friends give `StateFlow`s, and a Swift package whose equivalents are `@Observable` objects on the main actor. In both, a room's state carries the whole timeline, rebuilt from the changes on the library's thread. The socket is opened with `connect()` and closed with `disconnect()` (the bindings' objects have a `close` of their own, which frees them), and errors carry `status` and `detail` (Kotlin's exceptions have a `message` already).
