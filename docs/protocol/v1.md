# Nudge protocol v1

How clients talk to a Nudge host: a WebSocket for live views and plain HTTP for commands. The reasons are in [ADR 5](../adr/0005-nudge-owned-client-protocol.md). The TypeBox types in `@nudge/protocol` are the source of truth, and `packages/protocol/schema/v1.json` is generated from them; this page explains them.

> Draft. It describes the target of the work in progress and changes until the web UI and CLI use it.

Every path below is under `/v1/a/<assistant>`, apart from the assistant list. Bodies are JSON and are checked against the schema. Errors are `{ "error": "<message>" }` with status 400 (a bad body or cursor), 401 (no token, an unknown one, or a bad pairing code), 403 (an admin route, or renaming the lobby, for a player who isn't one), 404 (also for rooms the caller may not use) or 409 (an approval already decided). Where a client acts on what an error is, the body also has a `code`: `"rate_limited"` for a 429 that asks the client to wait (see [Limits](#limits)), and `"budget_spent"` for a message refused because a monthly budget is spent. Clients read a code they don't know as none.

### Limits

Every route under `/v1` but `/v1/health` is rate limited, in memory, so a restart forgets the counts. Each address gets 1200 requests at once and 20 a second after that, and each bearer token, wherever it is used from, 300 and 5 a second. The routes that take a code anyone could guess, `POST /v1/a/<assistant>/pair`, `POST /v1/sign-in` and every `POST` under `/v1/setup`, get 10 tries per address and one more every 30 seconds. Over a limit the reply is 429 with `Retry-After` (seconds) and `{ "error", "code": "rate_limited" }`; clients wait that long before trying again, and a message waiting in a client's outbox goes again by itself. `POST /v1/sign-in` answers the same code, without `Retry-After`, while too many sign-ins wait. A 429 with `"budget_spent"` is no rate limit: sending again won't help until the month ends or the budget changes. The address is the one that reached the server; behind a proxy (`server.trustProxy`) it is the last `X-Forwarded-For` entry, which the proxy added, and on Cloudflare `CF-Connecting-IP`. IPv6 addresses count by their /64.

A body over 1 MiB is refused with 413 and `{ "error" }` before the route reads it. Extension routes have limits of their own (see [Extension sockets](#extension-sockets)).

## Signing in

A player gets a token in one of two ways:

- `nudge invite <name>` or `nudge token <player>` prints one, as today.
- `nudge pair <player>` prints a one-time code as a link and a QR code: `nudge://pair?server=<url>&assistant=<name>&code=<code>`. The app sends `POST /pair { code, client: { name, platform } }` and gets `{ token, clientId, player }`. A code works once and expires after ten minutes. It looks like `7K3Q-M9XD` (Crockford base 32), so it can be typed too; case, dashes and spaces don't matter, and `O`, `I` and `L` read as `0`, `1` and `1`.

A browser signs in by an app that already is, with the QR code on the web UI's sign-in page. These two routes are the server's, outside any assistant, and need no token:

- `POST /v1/sign-in` answers 201, `{ id, secret, link, expiresAt }`: the page shows `link`, `nudge://sign-in?server=<url>&request=<id>`, as a QR code, and keeps `secret` to itself. A request works for five minutes, and is kept in memory, so a restart starts over; 429 while 500 are waiting.
- `GET /v1/sign-in/<id>`, with `Authorization: Bearer <secret>`, answers `{ status: "waiting" }` until an app approves, then `{ status: "approved", assistant, code }`; the page trades `code` at `POST /v1/a/<assistant>/pair` like any pairing code, with its own `client`. 404 once the request expired, and for a wrong secret.

The app, having asked the person, sends `POST /v1/a/<assistant>/sign-in/<id>` with its own token: 204, and the browser becomes that player at that assistant; 404 when the request expired or was approved already. The QR code holds only the id, so whoever photographs it can approve it but not use it. The browser may name the server by another address than the app, so the apps ask their other assistants too when the one at the link's server doesn't know it.

HTTP requests send `Authorization: Bearer <token>`. The socket sends the token in its first frame, because browsers can't set headers on a WebSocket.

A token works until it is revoked, unless it was issued with an expiry (`nudge token <player> --expires 30d`, or `expiresAt` to `POST /admin/tokens`), as for a script: from then on it is a 401, and sockets signed in with it close with 4401. Tokens from pairing and invites never expire. The server notes when each token last signed in a request or socket, to the minute (it writes that at most once a minute per token), and lists it as `lastUsedAt`; a socket that stays open isn't counted again until it reconnects.

## The socket

`GET /v1/a/<assistant>/connect` upgrades to a WebSocket. Frames are JSON text.

### Client to server

| Frame                                                                        | Meaning                                                              |
| ---------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `{ type: "hello", protocol: 1, token, client: { name, version, platform } }` | Must be first.                                                       |
| `{ type: "subscribe", target }`                                              | `target` is `"rooms"` or `"room:<id>"`.                              |
| `{ type: "unsubscribe", target }`                                            |                                                                      |
| `{ type: "ping" }`                                                           | Answered with `pong`. Send one if nothing arrived for `heartbeatMs`. |

### Server to client

| Frame                                                                                         | Meaning                                                        |
| --------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `{ type: "welcome", protocol: 1, server: { version }, epoch, player, clientId, heartbeatMs }` | Reply to a good `hello`.                                       |
| `{ type: "snapshot", target, seq, view }`                                                     | The whole view, first after `subscribe`.                       |
| `{ type: "patch", target, seq, ops }`                                                         | Changes since the previous frame for that target.              |
| `{ type: "unsubscribed", target, reason }`                                                    | `reason` is `"not-found"` or `"removed"` (no longer a member). |
| `{ type: "pong" }`                                                                            |                                                                |
| `{ type: "error", message }`                                                                  | A frame the server couldn't use; the socket stays open.        |

`seq` starts at 0 with the snapshot and goes up by one per frame for that target. A client that sees a gap, or a different `epoch` after reconnecting, subscribes again. Patches are sent at most every ~50 ms per target, so a slow client gets fewer, larger patches.

Close codes: 4400 bad frame, 4401 unknown token or revoked, 4404 no such assistant, 1001 the host is shutting down. A client retries with backoff on anything but 4400, 4401 and 4404.

### Patch operations

A path is an array of object keys and array indexes into the view.

| Op                                              | Effect                                                           |
| ----------------------------------------------- | ---------------------------------------------------------------- |
| `{ op: "set", path, value }`                    | Set the value at `path`, adding the key if it's new.             |
| `{ op: "del", path }`                           | Remove an object key.                                            |
| `{ op: "append", path, text }`                  | Append to the string at `path`. Streaming text arrives this way. |
| `{ op: "splice", path, index, remove, insert }` | Change the array at `path` like `Array.prototype.splice`.        |

Operations apply in order. An empty `path` with `set` replaces the whole view.

## Views

### `RoomView` (`room:<id>`)

```ts
{
  room: { id, kind: "lobby" | "personal" | "shared", name, members: Player[] },
  timeline: TimelineItem[],     // the most recent items, oldest first
  hasEarlier: boolean,          // more via GET /rooms/<id>/timeline
  live: { running: boolean, status?: Status },
  queue: { id, mode: "steer" | "followUp", text, author?, clientId?, requestId?, nudge: boolean, privateTo? }[],
  approvals: Approval[],        // pending ones and the ten latest decided, newest first
  memory: { id, text, createdAt, by?: Player, owner?: Player, privateTo?: Player }[], // the room's facts, then members' own shared ones (with owner)
  nudges: { id, message, fireAt, every?, privateTo?: Player }[],
  sharingLocation?: Player[],   // whose location the model may know here: a personal room's owner once known, in a shared room who chose to share it there
}

Player = { id, displayName, address? } // address: where someone from another assistant lives, such as "vegard@nudge.example.com/robin"
Approval = { id, summary, status, requestedAt, decidedBy?: Player, decidedAt?, result?, privateTo?: Player, adminOnly?: true } // adminOnly: only an admin may decide it
Status =
  | { kind: "retrying", attempt, at, error }
  | { kind: "compacting" }
  | { kind: "compaction-failed", error }

TimelineItem =
  | { type: "user", id, text, author?: Player, sentAt?, clientId?, requestId?, privateTo?: Player }
  | { type: "nudge", id, text, firedAt, privateTo?: Player }
  | { type: "approval", id, approvalId, summary, status, decidedBy?, privateTo?: Player }
  | { type: "answer", id, status: "running" | "done" | "stopped" | "failed", error?, parts: Part[], startedAt?, promptedBy?: "nudge" | "watch", privateTo?: Player }
  | { type: "marker", id, kind: "compacted" | "reset" }

Part =
  | { type: "text", text }
  | { type: "reasoning", text }
  | { type: "tool", callId, name, args, status: "pending" | "running" | "done",
      result?, isError?, details?, output?, truncated? }
```

Every view is the receiving player's own. Something private to another player (`privateTo` names them) comes emptied: a message or nudge with `text: ""`, an approval outcome with `summary: ""`, an answer with no parts, and private approvals, facts and nudges are left out. Text holds placeholders like `⟦EMAIL1⟧` where a value is hidden from the player, because someone else made it private or it was forgotten; show them as hidden, and the player's own private items as theirs alone.

Item ids are stable, so a client can key rows by them; an answer keeps its id from its first streamed token to its last entry. A user message carries the `requestId` its sender chose, in the timeline and while it waits in `queue`, so that sender can swap its optimistic copy for the real one. Tool `result` and `details` longer than about 8 KB are cut, with `truncated: true`. While a tool runs, `output` holds what it printed so far, and goes once `result` is there. Tools that report progress write one short line per step, ending in `…`, such as `browse`'s `Opening finn.no…` and `Clicking "Search"…`; a client shows the last non-empty line as the tool's live status. A tool part whose `details` has `approval` (an approval's id) asked for that approval, so a client can show its Approve and Deny there.

### `RoomListView` (`rooms`)

```ts
{
  player: Player,
  rooms: { room, running: boolean, pendingApprovals: number, lastItemAt? }[],
  nudges: { id, roomId, message, fireAt, every?, privateTo? }[],
  appearance?: Appearance,
}
```

`Appearance` is how the assistant's robot looks in the apps: `{ body: [colour, colour], eyes, sparks, eyeShape, accessory }`, colours as `#rrggbb` (`body` the ribbon's two ends), `eyeShape` one of `pill`, `round`, `square`, `wide`, and `accessory` one of `none`, `antenna`, `headphones`, `sprout`, `crown`. Absent, the apps draw the robot of the app icon, as they do for an eye shape or accessory they don't know. An admin's change reaches open room lists as a patch.

A `Profile` is `{ displayName, avatar?, timeZone?, language?, notifications?: { answers?, approvals? }, extensions? }`: `avatar` a base64 `data:image/…` URL of at most 64 KiB, `timeZone` IANA (the times of the player's nudges; the assistant's when absent), `language` BCP 47 (the assistant answers the player in it), `notifications` which pushes they get (each on unless `false`), and `extensions` each extension's settings for them by extension name: what they chose, without the defaults. `PATCH` replaces the extensions it names and leaves the others; `null` for one clears it. Each must fit the schema the extension declares (`GET /me/profile/extensions`), and an extension that isn't installed or takes no player settings is a 400. Changing `displayName` renames the player.

`PersonalDetails` are `{ fullName?, email?, phone?, address?, location?: { text, at }, locationRooms? }`, as the caller sees them, `locationRooms` the shared rooms where they share where they are (`PUT /rooms/<id>/location`). Each value goes into the vault as the caller's private value (as with `POST /protect` and `private`), so everyone else, and the model, only ever see its placeholder; the model is told the placeholders in the caller's personal room and their private messages, never elsewhere, and tools get the values. They are not part of the `Profile`, so a home doesn't send them to the assistants its players joined. `PATCH` takes `location` as `{ latitude, longitude, place? }`, `place` what the device calls the spot, such as a street address; it is kept as `"<place> (<lat>, <lon>)"` to four decimals, with `at` when it was sent. Its latitude and longitude are kept as values of their own too, so tools that take coordinates get numbers. A location within 100 m of the one before keeps its text and placeholders (only `at` changes), and one that replaces it, or `null`, forgets the old ones for good.

`whenBusy` is `"followUp"` (the default), `"steer"` or `"reject"`. Cursors are opaque strings. A message gets 429 with `"code": "budget_spent"` once the caller's or the assistant's monthly budget is spent (`budget` in `nudge.json`); `error` says whose, and clients show it rather than sending again.

`/timeline` without `before` starts just older than the room view's `timeline`; `before` from a page gets the page older than it, and a page without `before` reaches the start of the room. `limit` is 50 by default and at most 200; a page holds at least `limit` items, unless it is the last, and at most one more. Item ids match the room view's, so pages and the view join without gaps or repeats. Items that later slide out of the head of the room view's window stay valid: keep them rather than fetch them again.

## The server

`/v1/server` is the server's own API (ADR 11), for its owners rather than an assistant's admins: they create, change and delete assistants and set the model keys. An owner is someone who lives on one of the server's assistants, made one at setup or with `nudge owner add <player>`, or someone whose home is elsewhere, kept by their address (`nudge owner add <address>`). Someone who lives here trades their player token for a server token (`nudge_server_…`), sent as `Authorization: Bearer` like a player's; the two kinds don't stand in for each other. Someone whose home is elsewhere sends an assertion from their home's `POST /ext/federation/owner-assertion` instead, sealed for the server's own keys at `GET /server/key`, so any of their devices signs in, and no assistant here is needed for it: deleting one they joined leaves them an owner. Every route but `GET /server/key` and `POST /server/session` needs a server token, 401 without. Server tokens, like players', note when they were last used, and those from `nudge owner token <player> --expires 30d`, as for a script, stop working then; `nudge owner tokens` lists them.

### Setup mode

A server started with no config is in setup mode (ADR 11): it prints a one-time code, such as `ABCD-EFGH-JKMN`, and serves `/v1/setup`, for the web UI's setup page or an app, instead of any assistant. The code is typed like a pairing code (case, dashes and spaces don't matter). These routes need no token: the code in the body stands in for one. A wrong code is a 401, and ten of them close setup until the server restarts, as does the deadline a server made from the app is given; once setup is closed or done, every route but `GET /setup` answers 410. On a server that has a config, `/v1/setup` answers 404.

## Extension sockets

`GET /v1/a/<assistant>/rooms/<id>/ext/<extension>` upgrades to an extension's own socket for a room, such as the browser extension's live view. Send `{ "type": "hello", "token": … }` first and wait for `{ "type": "ready" }`; frames after that belong to the extension. It closes with 4401 for a bad token and 4404 when the assistant, the room (for this player) or the extension's socket doesn't exist. These frames are not part of protocol v1. The server passes every frame it sends through the same per-player view as the room's, so values others made private stay placeholders.

Extensions can serve HTTP routes of their own under `/v1/a/<assistant>/ext/<extension>/`, such as for other assistants or webhooks to call. Each route says who may call it: any player (a token, 401 without one), admins (403 for other players) or anyone. A body over the route's limit, 64 KiB unless it says otherwise, is a 413, and a path no route of the extension serves is a 404. What the routes take and answer is the extension's, not part of protocol v1.

## Push

Pushes come from the extension `push` (`extensions/push`), so its routes are under `/ext/push/` and answer 404 on an assistant without it. A room where it is turned off sends none.

A browser subscribed with `POST /ext/push/web` gets a Web Push when an answer finishes in one of the player's rooms (also an answer to a fired nudge or to an approval's outcome) and when an action there waits for approval. Pushes are encrypted for the browser (RFC 8291), so the push service in between can't read them. The service worker shows each as a notification unless the room is open in a visible tab of the site. By default notifications say only which room has news; the extension's `preview: "text"` adds the start of the text. A subscription stops getting pushes once the token that added it is revoked, and goes once the push service says the browser dropped it. When the browser replaces a subscription (`pushsubscriptionchange`), the service worker subscribes again with the same server key and sends `POST /ext/push/web/renew` to each assistant without a token: the old subscription's endpoint and `auth` secret, which only the browser and the server know (the push service sees the endpoint but not the secret), stand in for it, and the new subscription takes the old one's place, owned by the same player and client. A browser that drops a subscription without saying which (`oldSubscription` is null) can't prove anything, so the web UI posts its current subscription again on every load to each assistant it turned notifications on for. The extension makes the server's VAPID keys on first start, in `push-vapid.json` next to the database, and assistants whose databases are in the same directory share them: a browser has one subscription for the whole site.

The payload is JSON: `{ title, body, url, tag, kind: "answer" | "approval", roomId }`, with `url` the room's page (`/<assistant>/<room>`) and `tag` the same for every notification of a room, so a newer one replaces the older.

A device registered with `POST /ext/push/devices` gets the same through APNs or FCM, unless the player has that room subscribed on a socket at that moment (the apps disconnect in the background, so the server pushes then). APNs gets an alert with `title`, `body`, `thread-id` and `collapse-id` set to the room's `tag`, and `assistant`, `roomId`, `kind` and `url` beside `aps`. FCM gets a data message (`assistant`, `roomId`, `kind`, `url`, `title`, `body`, `tag`), high priority, collapsed by `tag`, and the app makes the notification. Both carry `account` too when the device registered one: an app signed in to two assistants of the same name, on two servers, tells their pushes apart by it. A device behind a relay (see the README) gets the same fields, sealed for its `deviceKey` into one string `v1.<epk>.<iv>.<data>.<tag>` (base64url: the push's own X25519 key, AES-256-GCM's IV, ciphertext and tag; the key is HKDF-SHA256 over X25519 between the two, salt `<epk>.<deviceKey>`, info `nudge push v1`, and the same string is the AAD). The relay puts it in a field `sealed`: in an APNs alert with `mutable-content`, whose title and body ("Nudge", "New message") the app's notification service extension replaces, or in an FCM data message. Registering the same `deviceKey` again replaces the old handle. A device token belongs to whoever registered it last, ten per player at most; tokens APNs or FCM call gone are forgotten, and so are those of revoked clients. The server sends with its own credentials: the extension's `apns` (a `.p8` key with its key id, team id and the app's bundle id) and `fcm` (a Firebase service account's JSON key) settings.

## Linked assistants

The extension `peers` (`extensions/peers`, ADR 16) lets assistants on different servers talk; it needs `federation` and its routes answer 404 on an assistant without it. ## The TypeScript client

`@nudge/client` (`packages/client`) does the client's side for TypeScript: `Connection` keeps the socket (hello, resubscribing after a reconnect or a gap, pings, backoff with jitter, giving up on 4400, 4401 and 4404), `RoomStore` and `RoomListStore` apply snapshots and patches (and fit React's `useSyncExternalStore`), and `Api` wraps the HTTP routes with a pluggable `TokenStore`. `NudgeClient` puts them together: leases on views, shared while held; `send` with a fresh `requestId`, shown as pending until the view has the message; an outbox, in a pluggable `KeyValueStorage` (the web app keeps it beside its token), whose messages that didn't get through are sent again with the same `requestId` when the socket opens and on `retryNow` (which the web app calls on `online` and when the page is shown again); and a room's earlier items, from `/timeline` pages and from the head of the view's window as it slides. Its tests replay the recorded stream and run against a real server.

## The Rust client

`clients/rust` does the same for Rust and, through UniFFI, for Swift, Kotlin and Python. `nudge-protocol` has the types, written by hand and checked against `schema/v1.json` and the recorded stream, and `apply`. `nudge-client` has `Api`, `Connection` (a task of its own, with the TypeScript client's reconnect, ping and give-up rules), `RoomListStore` and `RoomStore`, and `NudgeClient`, which adds a SQLite cache: the last view of every target, shown while reconnecting and after a restart, and an outbox. A message that doesn't get through waits there and is sent again, with the same `requestId`, once the socket is open; one the server refuses stays failed until it is sent again or dismissed. `nudge-ffi` runs a client on a Tokio runtime of its own and hands views to listeners: a room's timeline as changes (`Reset`, `Append`, `Insert`, `Set`, `Remove`), at most about 30 times a second, and tool arguments and details as JSON strings.

## The Python client

`clients/python` packages `nudge-ffi` as `nudge-client` (module `nudge`) with maturin, and adds an asyncio API: `Client` wraps the commands, and `connection()`, `room_list()` and `room(id)` return watches to iterate with `async for`, each state whole (the room's timeline rebuilt from the changes) and the latest only. Watches still open at exit are cancelled first, since a listener called during interpreter shutdown crashes Python. `FileTokens` keeps the token in a file only its owner can read.

## The Kotlin and Swift clients

`clients/android` and `clients/apple` wrap the same bindings: an Android library whose `observeRoomState(room)` and friends give `StateFlow`s, and a Swift package whose equivalents are `@Observable` objects on the main actor. In both, a room's state carries the whole timeline, rebuilt from the changes on the library's thread. The socket is opened with `connect()` and closed with `disconnect()` (the bindings' objects have a `close` of their own, which frees them), and errors carry `status` and `detail` (Kotlin's exceptions have a `message` already).
